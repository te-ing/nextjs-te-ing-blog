이직 후 마주한 새로운 프로젝트는 과도기적인 구조를 가지고 있었습니다. 바로 **Styled-components와 SCSS가 혼용**되어 사용되고 있는 환경이었습니다. 이 환경에서 가장 큰 불편함은 "코드의 위치를 찾는 것"이었습니다.

## 1. 문제 상황: 파편화된 스타일링과 위치 찾기의 어려움

기존 팀원들은 브라우저 개발자 도구에서 해당 요소의 위치를 유추하기 위해 고군분투하고 있었습니다.

- **SCSS 영역:** 개발자 도구에서 클래스명을 보고 위치를 파악하기 위해 `.checkin-wrapper`, `.order-item-list`와 같이 불필요하고 긴 접두사를 모든 클래스에 붙이고 있었습니다. 이는 코드 가독성을 해치고 작명 스트레스를 유발했습니다.
- **Styled-components 영역:** CSS-in-JS 특성상 클래스명이 해시값으로 변환되거나 컴포넌트 이름만 남기 때문에, SCSS처럼 접두사를 붙이는 방식조차 불가능했습니다. 결국 `Inspector`로 요소를 찍어도 소스 코드의 어디인지 한 번에 알 수 없었습니다.

이러한 불편함을 해결하기 위해 고민하던 중, 예전에 읽었던 [토스 기술 블로그: 나만의 Babel 플러그인 만들기](https://toss.tech/article/27750)의 사례가 떠올랐습니다. "우리가 직접 컴파일러 단계에서 위치 정보를 주입해주면 어떨까?"라는 생각으로 이어졌습니다.

## 2. 해결책: Babel 플러그인 제작

개발 환경에서 모든 JSX 요소에 해당 요소가 정의된 **파일명과 라인 번호를 `data-loc` 속성으로 자동 주입**해주는 Babel 플러그인을 제작했습니다.

### `babel-plugin-jsx-data-loc.cjs`

```javascript
/**
 * 개발 환경에서 JSX 요소에 data-loc 속성을 추가하는 Babel 플러그인
 * 해당 태그가 위치한 파일명과 라인 번호를 표시합니다.
 */
module.exports = function babelPluginJsxDataLoc({ types: t }) {
  return {
    name: 'babel-plugin-jsx-data-loc',
    visitor: {
      JSXOpeningElement(path, state) {
        const { filename } = state;
        if (!filename) return;

        // node_modules 파일 제외
        if (filename.includes('node_modules')) return;

        // Fragment 제외 (<> 또는 <React.Fragment>)
        const elementName = path.node.name;
        if (t.isJSXIdentifier(elementName) && elementName.name === 'Fragment')
          return;
        if (
          t.isJSXMemberExpression(elementName) &&
          elementName.property.name === 'Fragment'
        )
          return;

        // 이미 data-loc 속성이 있으면 스킵
        const hasDataLoc = path.node.attributes.some(
          (attr) =>
            t.isJSXAttribute(attr) && attr.name && attr.name.name === 'data-loc'
        );
        if (hasDataLoc) return;

        // 파일명만 추출 및 라인 번호 획득
        const fileName = filename.split('/').pop();
        const line = path.node.loc?.start?.line || 0;
        const locValue = `${fileName}:${line}`;

        // data-loc="파일명:라인번호" 속성 추가
        const dataLocAttr = t.jsxAttribute(
          t.jsxIdentifier('data-loc'),
          t.stringLiteral(locValue)
        );

        path.node.attributes.push(dataLocAttr);
      },
    },
  };
};
```

## 3. Vite 환경에서의 적용

Vite를 사용 중이라면 `@vitejs/plugin-react`의 `babel` 옵션을 통해 이 플러그인을 간단하게 적용할 수 있습니다. 운영 환경(Production)에는 영향이 없도록 개발 환경에서만 활성화합니다.

```javascript
// vite.config.js 예시
export default defineConfig(({ mode, command }) => {
  const isLocalDev = mode === 'development' && command === 'serve';

  return {
    plugins: [
      react({
        babel: {
          plugins: isLocalDev
            ? ['./plugins/babel-plugin-jsx-data-loc.cjs']
            : [],
        },
      }),
      // ...
    ],
  };
});
```

## 4. 도입 결과 및 변화

플러그인 도입 후, 팀의 개발 문화에 다음과 같은 긍정적인 변화가 생겼습니다.

1.  **작명 스트레스 해소:** 더 이상 위치 파악을 위해 SCSS 클래스명에 `.checkin-` 같은 불필요한 접두사를 붙일 필요가 없어졌습니다.
2.  **Styled-components 지원:** CSS-in-JS 요소도 개발자 도구에서 `data-loc="CheckInForm.tsx:24"`와 같이 소스 위치를 명확히 표시해줍니다.
3.  **커뮤니케이션 비용 감소:** 동료 개발자나 기획자와 화면을 보며 이야기할 때, "그 버튼 위치가 어디인가요?"라고 물어볼 필요 없이 바로 소스 코드를 열 수 있게 되었습니다.

## 5. 마치며: "왜"를 해결하기 위한 도구 만들기

단순히 라이브러리를 가져다 쓰는 것을 넘어, 현재 우리 팀이 겪고 있는 **구체적인 페인 포인트(Pain Point)**를 기술적으로 해결하려 노력했던 경험이었습니다.

토스 기술 블로그에서 보았던 아이디어를 우리 프로젝트의 상황(Styled-components + SCSS 혼용)에 맞게 변형하여 적용하면서, DX(Developer Experience)를 개선하는 즐거움을 다시 한번 느낄 수 있었습니다. 여러분도 팀 내에 반복되는 불편함이 있다면, 컴파일러 레벨에서의 해결책을 한 번 고민해보시길 추천합니다.
